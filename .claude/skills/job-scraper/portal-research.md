# Job Source Research: Signal Quality for Sahil's Nov 2026 Search

Date of research: 2026-08-25. Candidate: Sahil Singh Diwan (AI/GenAI engineer, Bengaluru, on notice, last working day 12 Oct 2026, target offer by mid-to-late Nov 2026, ₹25-40 LPA fixed, RAG/agentic/LangChain background). Existing skills: `linkedin-search`, `naukri-search`, `instahyre-search`, `freehire-search`.

Everything below is a live-research finding unless marked **[inferred]** or **[unverified]**. Where I guessed an API shape and it didn't work, I've said so rather than omitting it — see the note in the brief about that being the failure mode to avoid.

## 1. Top recommendations — build these next, in order

**1. Greenhouse Job Board API, as a "known-company lookup" tool, not a discovery crawler.** `https://boards-api.greenhouse.io/v1/boards/{slug}/jobs?content=true` is a real, unauthenticated, JSON endpoint — verified live against `anthropic` (200 OK, full job objects with `title`, `location`, `updated_at`, `content`). robots.txt on `boards-api.greenhouse.io` disallows only `/embed/` — nothing blocks any bot, including Claude. This is the highest signal-to-noise data available anywhere: it's the employer's own ATS feed, no repost, no agency, a real `updated_at` timestamp. The catch, and it's real: there's no directory to enumerate slugs from. The tool's value is "given a company name Sahil is targeting (from a VC portfolio list, a funding announcement, or a LinkedIn careers link), fetch its Greenhouse feed in one HTTP call and get every open req with real dates" — a lookup utility, not a `/scrape` crawler. Given the Nov deadline, this is the single highest-leverage thing to build: point it at 30-40 named AI-first Indian and remote-friendly startups and re-run weekly.

**2. Ashby Job Board API, same lookup pattern.** `https://api.ashbyhq.com/posting-api/job-board/{slug}` — verified live against `ramp`, returned full job objects (title, department, location, `isRemote`, `workplaceType`, `publishedAt`). Ashby is the fastest-growing ATS among frontier-AI and well-funded startups specifically (it's the "cool new one"), so it overlaps unusually well with Sahil's target sector. Build alongside Greenhouse as one combined "check these N companies' ATS feeds" skill.

**3. SmartRecruiters API, same pattern, lower priority than the two above.** `https://api.smartrecruiters.com/v1/companies/{slug}/postings` — verified live, real JSON, real dates. Caveat: `api.smartrecruiters.com/robots.txt` disallows `/` for all user-agents except `LinkedInBot` — the only ATS host I found with a blanket-disallow posture rather than a narrow one. It doesn't name Claude specifically, but the intent ("stay out, unless you're LinkedIn") is clear. Worth having in the toolkit for the handful of companies that use it, but don't lead with it, and consider it ethically closer to the Naukri/RemoteOK line than to Greenhouse/Ashby.

**4. WeWorkRemotely, as an HTTP-scrapeable page (not an API).** robots.txt is fully open (`Allow: /`, only account/admin paths blocked), no AI-bot rule found anywhere in it. Live search for "AI engineer" returned real, mixed-geography listings, some with salary, all with relative posting dates, no sign of the Instahyre stale-listing problem. It won't be India-specific — most postings are "Anywhere in the World" or US/EU-gated — so the skill needs to filter hard on the "location restriction" line in each posting rather than trust a location filter. Still the cleanest global-remote board found this round, and building it as a plain HTTP CLI is straightforward (no JS rendering needed for the search results themselves per this fetch).

**5. A manual (not automated) VC-portfolio pass on Peak XV, Lightspeed, and Blume.** These three run on real, structured platforms (`careers.peakxv.com` and `jobs.lsvp.com` on "Consider"; `jobs.blume.vc` and Accel's `jobs.accel.com` on "Getro") pre-filtered to exactly "funded startup, often AI-heavy, India-relevant." Neither platform exposes a documented free public API to job-seekers — Getro's own robots.txt is a plain-text note asking bots to use their (evidently paid/permissioned) API instead of scraping, and I found no equivalent notice or API for Consider, just no evidence of one either. Building an automated skill here means either a paid Getro contract or `ego-browser` scraping against an operator's explicit "please don't scrape, call our API" ask — not a great trade for a CLI-first repo. Given the November deadline, the better move is a manual weekly 15-minute browse of these three boards rather than a build.

## 3. Per-source detail

### Greenhouse
- Endpoint: `GET https://boards-api.greenhouse.io/v1/boards/{board_token}/jobs?content=true` — verified against `anthropic`, 200 OK, returned `absolute_url`, `location`, `updated_at`, `first_published`, `metadata` (often includes a "Location Type" field distinguishing remote/hybrid/on-site — directly useful for the remote-eligibility question).
- No enumeration endpoint. The `board_token` is usually the company's URL slug on `job-boards.greenhouse.io/{slug}` — find it from the company's own "Careers" link, not by guessing.
- robots.txt: only `/embed/` disallowed, for all user-agents. No Claude/AI-bot rule.
- A portal skill here would take a list of company slugs (maintained manually or seeded from VC portfolio pages) and hit each one's `/jobs` endpoint, diffing against previously-seen job IDs — cheap, testable, CI-able exactly as the repo wants.

### Ashby
- Endpoint: `GET https://api.ashbyhq.com/posting-api/job-board/{board_name}` — verified against `ramp`, returned full nested job objects with `secondaryLocations`, `isRemote`, `workplaceType`, `publishedAt`.
- `jobs.ashbyhq.com/robots.txt` (the human-facing board) disallows `/api/`, but the actual data API lives on the separate `api.ashbyhq.com` host, whose own `/robots.txt` path itself returned HTTP 401 (an API-auth wall on the robots.txt route specifically, not a policy statement) — inconclusive on paper, but the documented posting-api path answered unauthenticated in practice.
- Same enumeration limitation as Greenhouse: need the slug in advance.

### Lever
- Two hosts, two different postures — this matters:
  - `api.lever.co/v0/postings/{slug}?mode=json` — data API, robots.txt says `Allow: /`, `Crawl-delay: 1` for all UAs. Verified: `lever` (the company) returns `[]` (valid empty array, real schema, just not hiring), and unknown slugs return a clean `{"ok":false,"error":"Document not found"}` — good, unambiguous error handling, not a silent wrong-looking success.
  - `jobs.lever.co` — the candidate-facing board, has a Cloudflare-managed robots.txt block that explicitly names `ClaudeBot: Disallow: /`, even though a later generic `Allow: /` block exists in the same file (the specific bot rule should govern). **Use the API host, never the board host, for anything Claude-driven.**
- Could not find a live example company with open jobs in the time budget (several guesses 404'd cleanly) — the endpoint shape is confirmed correct by the schema and error behavior, but I have no confirmed non-empty real-world payload to show.

### SmartRecruiters
- Endpoint: `GET https://api.smartrecruiters.com/v1/companies/{slug}/postings` — verified against `SmartRecruiters` itself: 8 real postings, `releasedDate`, `location.remote`/`hybrid` flags, `department`, `experienceLevel`.
- robots.txt: `Disallow: /` for `User-agent: *`, with a narrow `Allow: /v1/companies/` carved out only for `LinkedInBot`. This is the one ATS host that reads as "we'd rather only LinkedIn crawl this." Doesn't name Claude, but the operator's intent is explicit exclusion of general bots. Use with more caution than Greenhouse/Ashby.

### Workable
- robots.txt is unusually explicit about AI use via `Content-Signal` (`search=yes, ai-input=yes, ai-train=no`), which reads as "fine for retrieval/RAG use, not for training" — a genuinely permissive stance for the exact use case here (an agent looking up jobs). But I could not find the actual working data endpoint in this session: `apply.workable.com/api/v1/widget/accounts/{shortcode}` returned "Not Found" for both `workable` and a guessed real user (`braze`), and `apply.workable.com/api/v3/accounts/{slug}/jobs` also 404'd. Either the shortcodes I tried are wrong or the endpoint shape has changed. **Do not build against these paths without finding a confirmed-working example first.**

### Recruitee
- robots.txt is the most explicitly AI-bot-friendly of any site checked: separate blocks for GPTBot, ChatGPT-User, and ClaudeBot, all with `Allow: /` (only excluding preview/tracking-parameter paths shared with the marketing site). A real signal this operator wants AI agents reading their content.
- Could not confirm a working candidate-facing job API in this session (one guessed shape, `/api/c/{id}/offers`, 404'd). Worth a follow-up look given how welcoming the robots.txt is.

### Zoho Recruit
- Confirmed real companies run career sites on it: `increff.zohorecruit.com` (Increff, a real Bengaluru retail-AI company), `careers.zohorecruit.in`, `thehireboost.zohorecruit.com`.
- `recruit.zoho.com/robots.txt` (the parent domain's rules, which the per-tenant `*.zohorecruit.com` sites appear to inherit in spirit) explicitly allows `/jobs`, `/jobs/`, `/jobs/*`, `/careers`, `/ats/ViewJob.na`, `/recruit/downloadrssfeed`, `/recruit/sitemapfeed` for all user-agents — no bot exclusions found.
- But: fetching `increff.zohorecruit.com/careers` returns a client-rendered single-page app shell (verified: 1,124 lines of HTML, zero job-listing content, only CSS/JS bundle references like `portalHandler.js`). The `downloadrssfeed` path, hit bare, redirects into a Zoho account sign-in page rather than returning a feed — it almost certainly needs a per-tenant `portal_id`/`page_id` query parameter that isn't published anywhere I found.
- **This is the ATS-vs-board distinction the brief asked about, concretely**: Zoho Recruit is legitimately used by real employers and its robots.txt is wide open, but there is no clean documented public API the way there is for Greenhouse/Ashby/Lever/SmartRecruiters. A portal skill here would need either (a) `ego-browser` per company, which is exactly the "expensive, brittle, no test coverage" path the repo wants to avoid, or (b) reverse-engineering the internal AJAX calls behind `portalHandler.js` per tenant, which risks the same "looks like it works, silently doesn't" trap flagged in the brief. **Recommend: treat Zoho Recruit as a manual-search target** (`site:zohorecruit.com bengaluru AI engineer` style queries) rather than an automated skill, until a cleaner endpoint is found.

### VC portfolio boards (Consider / Getro)
- Peak XV (`careers.peakxv.com`) and Lightspeed India (`jobs.lsvp.com`) both carry the "Powered by Consider" mark and reference `consider.com` in their page markup — confirmed live.
- Accel (`jobs.accel.com`) and Blume Ventures (`jobs.blume.vc`) both reference Getro CDN hosts (`cdn.getro.com`, `an.getro.com`, `cdn-customers.getro.com`) — confirmed live. Their robots.txt is not a rules file at all but a plain-text message: *"We'd be happy to provide all job data to you through our API services. It's more cost-effective than using proxies. Please contact us at api@getro.com..."* — no `Disallow` line exists, so scraping isn't technically blocked by the file's syntax, but the operator's stated preference is unambiguous: pay for the API, don't scrape the pages.
- Elevation Capital has no equivalent structured board — just a generic careers page pointing to Glassdoor/LinkedIn. Drop from this category.
- No client-facing JSON endpoint was found on either platform in light inspection (checked page markup for API call patterns; found none beyond internal CDN asset references).
- **Given the operator's explicit "talk to us about the API" ask, and no free/anonymous version of that API being evident, the honest recommendation is manual browsing, not scraping** — these three (Peak XV, Lightspeed, Blume) are worth 15 minutes a week of human attention given how precisely they match "funded India-relevant AI-adjacent startup," but not a build target right now.

### Wellfound
- Confirmed salary transparency: the one clearly-Bangalore listing found (`DhronAI — AI Engineer`) showed `₹20,000–₹50,000, no equity`, and the broader global results showed real `$` ranges too. This is a genuinely different posture from Naukri.
- Posting dates present and looked fresh (`7 days ago` on the one Bangalore listing) — no sign of Instahyre's staleness problem, though the sample was small.
- robots.txt disallows `/search`, several query-string patterns (`?jobId=`, `?role=`, `?preview=`), `/re/`, `/recruit/dashboard`, and others — the disallowed set looks aimed at authenticated/dashboard/apply flows and the live-search backend specifically, not the static `/role/l/{role}/{location}` browse pages I fetched successfully. No AI-bot name found anywhere in the file.
- Volume for Bengaluru specifically looked thin in this pass, but I'm not confident in that as a hard number — the fetch tool may have truncated a longer results page. Treat "thin" as directional, worth a second, deeper check before deciding not to build.

### Himalayas — the biggest surprise
- 240 total results for "AI Engineer" is a real number, with real salaries and real relative dates, and the page structure looked clean (no obvious spam).
- The single most important finding in this whole research round: filtering explicitly to India as a location still surfaced a page where roughly 18 of ~20 visible listings were geography-gated to somewhere else entirely (`United States only`, `Germany only`, `Brazil only`), with only 2 explicitly saying `India only`. **A location filter that returns wrong-country results by an 9:1 margin is worse than no filter, because it creates false confidence.** Any skill built against Himalayas (or by extension, any "remote" board using a similar filter architecture) must re-parse the actual eligibility line on every listing rather than trust the filter parameter.

### RemoteOK
- The free JSON API at `remoteok.com/api` is real and returned genuine current data with no authentication in this session's test — technically the easiest global-remote source to build against of everything checked.
- But its robots.txt is unambiguous: `User-agent: ClaudeBot / Disallow: /`, in the same Cloudflare-managed block that also excludes Amazonbot, Applebot-Extended, Bytespider, CCBot, and a Cloudflare rendering crawler — i.e., it's specifically excluding AI-agent traffic by name, the identical pattern to Naukri. The fact that a plain `curl` call succeeded anyway (no active enforcement observed in this light, one-off test) doesn't change what the policy says. **Recommend not building this one, on the same grounds Naukri was excluded** — this is a case where "it works" and "it's allowed" diverge, and the brief is explicit that evasion isn't the goal here.

### WeWorkRemotely
- Fully open robots.txt, real listings with salary sometimes shown and always a relative post date, no evidence of an ATS/agency slop pattern in the sample checked. Geographic eligibility is genuinely mixed — "Anywhere in the World" appears next to hard-gated regional postings — so an eligibility filter is necessary but at least the underlying data supports building one (postings do state their own scope in plain text).

### Remotive
- Could not get past a live interactive Cloudflare JS challenge just to read `robots.txt` — this is a stronger wall than any Disallow rule found elsewhere in this research, since it blocks even policy discovery via plain HTTP. Whatever API/RSS this site reportedly has (commonly mentioned online) is unconfirmed by me; building against it would require a real browser session, which raises the same cost/brittleness concerns as Zoho Recruit and the VC boards. Deprioritize.

### ai-jobs.net / aijobs.net
- Best robots.txt of anything checked (`Allow: /`, only `/account/` blocked, no bot names at all).
- However, every specific API/feed URL I tried based on a secondary source's description of the site's "documented JSON API" — `/api/list-jobs/`, `/api/v1/jobs`, `/feed/`, on both the `ai-jobs.net` and `aijobs.net` domain forms — returned a clean 404 "Page not found," not an error that looks like a wrong parameter. This is precisely the failure mode the brief called out: a plausible-sounding endpoint that simply isn't real, discovered only by testing it live rather than trusting a description. If this site is worth pursuing later, the real path needs to be found first (likely by inspecting the rendered site's own outbound requests, not by guessing from an old blog post).

### Aggregator APIs (Adzuna, Arbeitnow, Jooble, JSearch, Careerjet, Google Jobs)
- None of these were live-tested with real credentials — Adzuna and JSearch both require account signup, which I didn't do (out of scope for pure research). Their existence, free-tier limits, and general shape are corroborated by their own developer-portal pages and third-party comparison write-ups, but treat the specific numbers (1,000 calls/month for Adzuna, ~200 for JSearch) as **reported, not independently confirmed**.
- The one thing verified live: Careerjet's robots.txt blocks `/job/`, `/jobview/`, `/jobviewx/` — the exact paths that would carry individual listing content — while leaving the shell open. That's a real, live-confirmed technical block on the content that matters.
- JSearch's most useful property for this repo, per its own vendor comparison material, is that it explicitly does **not** cover ATS-direct postings (no Greenhouse/Lever/Ashby/Workday) — meaning it duplicates the aggregator-board space rather than substituting for the ATS-lookup approach in recommendation #1. Not a priority build.

## 4. What to drop or deprioritize

- **Naukri: confirmed correctly excluded.** Live fetch of `naukri.com/robots.txt` reproduces exactly what the user reported — `Claude-User`, `Claude-SearchBot`, `claudebot`, `meta-externalagent`, `gptbot`, and several others named explicitly with `Disallow: /` on all job content, only carving out blog/career-advice paths. Combined with the independently-reported 17/20-single-employer and 0/20-salary findings, there is no case for un-deprioritizing this. Verdict: **leave excluded, don't build an HTTP path around it.**
- **Instahyre: candidate for demotion.** The existing skill presumably already uses `ego-browser` given that a plain fetch returned 403 this session (login-gated, consistent with the original build choice). The already-reported staleness (11 to 649-day-old listings rendering identically) is a real signal-quality problem independent of the access method — a portal that can't distinguish a live req from a dead one wastes review time regardless of how the data gets in. Recommend keeping it in rotation at reduced priority (e.g., biweekly instead of every run) rather than fully cutting it, since it's already built and some real Bengaluru tech roles clearly do exist there — but stop treating its result count as a volume signal.
- **RemoteOK: do not build**, despite the tempting free API, on the same robots.txt grounds as Naukri (explicit `ClaudeBot: Disallow: /`).
- **Foundit: do not build.** Same explicit-AI-bot-block pattern as Naukri, found live in its robots.txt, naming ClaudeBot/GPTBot/CCBot/Bytespider/Meta-ExternalAgent/Google-Extended and blocking `/jobs/` and `/search/` specifically for them.
- **Careerjet: skip.** robots.txt blocks the job-detail paths outright; there's nothing to scrape even if the shell is open.
- **Otta: doesn't exist anymore** as an independent product — folded into Welcome to the Jungle. Remove from any future list as a separate source.
- **Cutshort: not useful for this candidate's use case as currently understood.** Its public API is employer-side (search candidates, post jobs), not a job-search API — building against it wouldn't help Sahil find jobs. Its own `llms.txt` self-description is marketing copy and shouldn't be cited as fact (e.g. "every 3rd high-skill developer" is a vendor claim, not measured). If Cutshort is worth anything here, it's as a manually-browsed board, unverified in this pass.
- **Hirist/iimjobs: low priority, not because of policy but because of cost.** robots.txt is actually fine (no AI-bot names, unlike Naukri/Foundit/RemoteOK), but the content is JS-rendered and returned nothing useful to a plain fetch — building this cheaply would need real browser rendering, and I found no evidence yet that the resulting volume/quality would justify that cost relative to Greenhouse/Ashby/WeWorkRemotely.
- **Elevation Capital, Otta/WTTJ, Hugging Face jobs, Arbeitnow, Jooble: not enough evidence either way** to recommend building or dropping — genuinely unresearched or inconclusive this round, listed for completeness, not as a "do this later" queue.

## 5. Non-board channels (brief)

- **Direct-to-company applications, once an ATS slug is known**, is the natural payoff of recommendation #1 — skip the board layer entirely and apply through the employer's own Greenhouse/Ashby/Lever page. Fastest path to a real hiring manager, zero board slop.
- **Founder/VC Twitter and AI-specific Discords/Slacks**: genuinely valuable given the compressed timeline — hiring managers at small AI-first teams often post roles there before any board, and response times are typically faster than an ATS queue. Inherently manual and relationship-driven; not a scrape target, but worth 15-20 minutes a few times a week between now and the November deadline.
- **Blind**: useful for real (if anonymous, unverifiable) comp-band and interview-process intel on specific companies once a target list exists, not for job discovery itself. Requires an account/session; not worth automating.
